Gateway encapsulates access to an external system or resource behind an object that presents a useful application-facing interface. The application should not need to understand the quirks of every remote API, SDK, protocol, or data source it talks to.

## The Problem

Suppose application code directly uses a payment provider's SDK:
``` csharp
var client = new VendorPaymentClient(apiKey);

var response = await client.CreateChargeAsync(
    new VendorChargeRequest
    {
        AmountInMinorUnits = 12500,
        Currency = "usd",
        SourceToken = token
    });
```

Now vendor terminology and transport details have leaked into application logic. A Gateway creates a boundary.

## An Application-Facing Interface

``` csharp
public interface IPaymentGateway
{
    Task<PaymentAuthorizationResult> AuthorizeAsync(
        Money amount,
        PaymentMethodToken paymentMethod,
        CancellationToken cancellationToken);
}
```

Application code speaks its own language:
``` csharp
var authorization =
    await payments.AuthorizeAsync(
        order.Total,
        command.PaymentMethod,
        cancellationToken);
```

The implementation handles the external system.

## Vendor-Specific Implementation

``` csharp
public sealed class VendorPaymentGateway(
    VendorPaymentClient client)
    : IPaymentGateway
{
    public async Task<PaymentAuthorizationResult>
        AuthorizeAsync(
            Money amount,
            PaymentMethodToken paymentMethod,
            CancellationToken cancellationToken)
    {
        var response =
            await client.CreateAuthorizationAsync(
                new VendorAuthorizationRequest
                {
                    Amount = ToMinorUnits(amount),
                    Currency = amount.Currency,
                    Token = paymentMethod.Value
                },
                cancellationToken);

        return Map(response);
    }
}
```

Vendor DTOs remain inside the gateway.

## Gateway Is Translation

A useful Gateway does more than rename SDK methods. It translates between two models:
``` text
Your application
    |
IPaymentGateway
    |
Vendor protocol / SDK
```

That translation may include:
-   request mapping,
-   response mapping,
-   error translation,
-   authentication,
-   retries,
-   idempotency keys,
-   protocol details.

## HttpClient

A modern HTTP gateway can use a typed `HttpClient`:
``` csharp
public sealed class ShippingGateway(
    HttpClient httpClient)
{
    public async Task<ShippingQuote> GetQuoteAsync(
        Shipment shipment,
        CancellationToken cancellationToken)
    {
        var request = ShippingRequest.From(shipment);

        using var response =
            await httpClient.PostAsJsonAsync(
                "/quotes",
                request,
                cancellationToken);

        response.EnsureSuccessStatusCode();

        var dto =
            await response.Content
                .ReadFromJsonAsync<ShippingQuoteDto>(
                    cancellationToken);

        return dto!.ToDomain();
    }
}
```

Dependency injection can configure the client centrally.

## Translate Failures

Do not force the rest of the application to understand vendor exceptions:
``` csharp
catch (VendorRateLimitException)
```

The Gateway can translate them into application-relevant failures:
``` csharp
throw new ShippingProviderUnavailableException(
    "The shipping provider is temporarily unavailable.",
    exception);
```

Preserve enough diagnostic information for operations without coupling application logic to vendor types.

## Resilience

Network gateways must account for transient failures. Potential policies include:
-   timeout,
-   retry,
-   circuit breaking,
-   rate limiting.

But retries are not automatically safe. A payment operation that creates a charge may require an idempotency key before retrying. Resilience belongs to the semantics of the operation, not merely to an HTTP client configuration checkbox.

## Gateway vs. Repository

Repository represents access to a collection of domain objects, usually through persistence. Gateway represents access to an external resource or subsystem. A database can have a Gateway, especially in lower-level Data Mapper designs, but in application architecture the distinction is useful:
``` text
Repository -> domain-oriented persistence
Gateway    -> external-system boundary
```

## Gateway vs. Remote Facade

Remote Facade is built by the server to expose a coarse-grained remote interface. Gateway is built by the client side to consume an external interface. They can face each other across the same network:
``` text
Service A Gateway
       |
     HTTP
       |
Service B Remote Facade
```

## Anti-Corruption Boundary

In domain-heavy systems, a Gateway often acts as part of an anti-corruption layer. If the vendor calls something a `ContractAccount` while your domain calls it a `Subscription`, the Gateway can translate instead of importing the vendor's conceptual model throughout the codebase.

## Testing

Application tests can substitute the gateway interface:
``` csharp
var payments =
    new StubPaymentGateway(
        PaymentAuthorizationResult.Approved(...));
```

But the real Gateway still needs integration or contract tests against:
-   a sandbox,
-   a test server,
-   recorded fixtures,
-   a protocol-compatible fake.

Mocking the interface does not prove the integration works.

## Observability

Gateways are excellent places to capture:
-   dependency latency,
-   failure rates,
-   request correlation,
-   retry counts,
-   provider status.

Avoid logging secrets, credentials, or sensitive payloads.

## When to Use It

Use Gateway when an external API, service, SDK, file format, or subsystem would otherwise leak its details into application code.

## When Not to Overdo It

A wrapper that exposes the vendor API method-for-method under different names may add little value. The Gateway earns its place when it creates a meaningful boundary and translation layer.

## Related Patterns

## Summary

Gateway gives your application a stable, intentional interface to something it does not control. In modern .NET, typed `HttpClient` integrations and vendor SDK adapters are common implementations. A good Gateway keeps external terminology, protocols, errors, and change pressure at the edge of the system.

Plugin links implementations to an application at configuration or runtime rather than hard-coding them into the core. The application defines a stable contract. Independent components implement that contract. Configuration or discovery decides which implementations participate.

## The Core Idea

Define a contract:
``` csharp
public interface IReportExporter
{
    string Format { get; }

    Task ExportAsync(
        Report report,
        Stream destination,
        CancellationToken cancellationToken);
}
```

Implementations can live independently:
``` csharp
public sealed class CsvReportExporter
    : IReportExporter
{
    public string Format => "csv";

    public Task ExportAsync(
        Report report,
        Stream destination,
        CancellationToken cancellationToken)
    {
        // ...
    }
}
```

The core application depends on the interface, not on every implementation.

## Compile-Time Plugins with DI

The simplest modern .NET plugin mechanism is dependency injection:
``` csharp
builder.Services.AddSingleton<
    IReportExporter,
    CsvReportExporter>();

builder.Services.AddSingleton<
    IReportExporter,
    PdfReportExporter>();
```

Then:
``` csharp
public sealed class ExporterRegistry(
    IEnumerable<IReportExporter> exporters)
{
    // ...
}
```

The implementation set is chosen at composition time. That is already a useful form of Plugin.

## Separate Assemblies

A stronger plugin boundary uses separate projects:
``` text
Reporting.Contracts
Reporting.Core
Reporting.Plugin.Csv
Reporting.Plugin.Pdf
```

The contracts assembly contains only the stable interface and shared contract types. Plugin assemblies reference the contracts package. The core does not need compile-time knowledge of each plugin implementation.

## Discovery

At runtime, the application can scan a plugin directory:
``` text
/plugins
    Reporting.Plugin.Csv.dll
    Reporting.Plugin.Pdf.dll
```

Load assemblies, find concrete types implementing:
``` csharp
IReportExporter
```

and register or instantiate them. Reflection-based discovery is appropriate when runtime extensibility is an actual requirement. Do not introduce assembly scanning merely to avoid a few explicit DI registrations.

## AssemblyLoadContext

Modern .NET provides `AssemblyLoadContext` for advanced loading scenarios. A custom load context can help:
-   isolate dependencies,
-   load plugin assemblies dynamically,
-   unload plugin contexts,
-   resolve plugin-specific dependencies.

This becomes important for genuine extensibility platforms. It also introduces substantial complexity.

## Contract Identity

A plugin and host must agree on the identity of shared contract assemblies. If the host and plugin each load incompatible copies of the contract assembly, a type that *looks* like `IReportExporter` may not be assignable to the host's `IReportExporter`. Plugin loading requires deliberate dependency resolution.

## Plugin Metadata

A plugin often needs metadata:
``` csharp
public sealed record PluginDescriptor(
    string Id,
    Version Version,
    string DisplayName,
    IReadOnlySet<string> Capabilities);
```

The host can validate compatibility before activation. This is more robust than assuming every DLL in a folder is safe and compatible.

## Versioning

Once third parties can build plugins, your interface becomes a public API. Changing:
``` csharp
Task ExportAsync(Report report);
```

to an incompatible signature can break every plugin. Use:
-   semantic versioning,
-   additive evolution where possible,
-   capability discovery,
-   compatibility checks,
-   documented lifecycle policies.

Plugin contracts should change more slowly than internal code.

## Security

Loading arbitrary assemblies means executing arbitrary code inside your process. A plugin can potentially:
-   read process memory,
-   access files,
-   make network requests,
-   consume CPU and memory,
-   crash the process.

`AssemblyLoadContext` is not a security sandbox. Untrusted plugins generally require a stronger process or container boundary.

## Process Isolation

For untrusted or failure-prone extensions, consider:
``` text
Host
  |
IPC / HTTP / gRPC
  |
Plugin Process
```

The plugin becomes more like an external service. That costs more operationally but creates a real isolation boundary.

## Dependency Injection for Plugin Dependencies

Plugins may need host-provided services:
``` csharp
public sealed class CsvExporter(
    ILogger<CsvExporter> logger,
    TimeProvider timeProvider)
    : IReportExporter
{
}
```

A plugin activation mechanism can create implementations through the host's service provider. Be deliberate about which host services form part of the plugin contract.

## Plugin Configuration

Each plugin may have its own options:
``` csharp
public sealed class CsvExporterOptions
{
    public char Delimiter { get; init; } = ',';
}
```

Configuration can determine whether the plugin is enabled and how it behaves. This is often simpler than runtime discovery when the plugin set is known at deployment time.

## Registry

Plugin and Registry work naturally together. Plugins provide implementations. A Registry chooses one:
``` csharp
var exporter =
    exporters.Get(requestedFormat);
```

The Registry does not need to know whether the implementation was statically registered or dynamically loaded.

## Testing

Test plugin systems at several levels. Contract tests verify every implementation obeys expected semantics. Loader tests verify:
-   discovery,
-   compatibility,
-   duplicate IDs,
-   missing dependencies,
-   invalid assemblies,
-   unload behavior if supported.

Integration tests verify real plugins inside the host.

## When to Use It

Plugin is useful when:
-   implementations vary by deployment,
-   third parties extend the application,
-   optional features should remain decoupled,
-   runtime or configuration-time extensibility is a real requirement.

## When to Keep It Simple

If your application has exactly two implementations that ship together forever, ordinary DI may be enough. A dynamic plugin platform has significant costs in loading, compatibility, versioning, diagnostics, and security.

## Related Patterns

-   Separated Interface
-   Registry
-   Gateway
-   Service Stub

## Summary

Plugin separates stable application contracts from replaceable implementations. Modern .NET supports the simple end of the spectrum through dependency injection and the advanced end through separate assemblies and `AssemblyLoadContext`. Use the lightest mechanism that satisfies the actual extensibility requirement - and never mistake in-process loading for a security boundary.

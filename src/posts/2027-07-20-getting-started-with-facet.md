Facet starts from a different question than every other tool in this series. AutoMapper, Mapster, Mapperly, and manual mapping all assume you've already written the destination DTO class, and focus on generating the code that populates it. Facet asks why you wrote that class by hand at all - given a domain model and a declarative attribute describing which fields matter for a specific view, it generates both the DTO type and the mapping code from a single source generator pass.

This guide covers installing Facet, bootstrapping your first generated facet from a domain model, the core patterns for excluding fields and generating multiple views of the same entity, and the best practices for using it specifically where its narrower, DTO-generation-focused approach fits better than a general-purpose mapper. By the end you'll have eliminated a category of boilerplate the rest of this comparison series doesn't even attempt to address.

If you're deciding between mapping approaches first, [a comparison of the top .NET mapping libraries](/posts/2027-06-22-top-5-dotnet-mapping-libraries-compared/) covers where Facet fits relative to AutoMapper, Mapster, Mapperly, and manual mapping - including why it's solving a narrower, more specific problem than a general-purpose mapper.

## What You'll Need

- .NET 8 SDK or later
- A recent C# language version, since Facet relies on source generators
- A codebase where the dominant pattern is "generate a focused view of a domain entity" - Facet is a more specific fit for this than for arbitrary type-to-type mapping

## Installing Facet

```bash
dotnet add package Facet
```

## Bootstrapping the Ideal Environment

### Generating a DTO directly from a domain model

```csharp
public class User
{
    public int Id { get; set; }
    public string FirstName { get; set; } = "";
    public string LastName { get; set; } = "";
    public string Email { get; set; } = "";
    public string PasswordHash { get; set; } = "";
    public DateTime CreatedAt { get; set; }
}
```

```csharp
[Facet(typeof(User), exclude: [nameof(User.PasswordHash)])]
public partial class UserDto;
```

That's the whole declaration. The `[Facet]` attribute, pointed at `User` and excluding `PasswordHash`, generates the full `UserDto` class - every property from `User` except the excluded one - along with the mapping code to populate it from a `User` instance. There's no separate DTO class body to write by hand at all.

### Using the generated facet

```csharp
var user = await db.Users.FindAsync(userId);
var dto = new UserDto(user); // constructor generated by Facet
```

Facet generates a constructor (or, depending on configuration, a static factory or extension method) that performs the mapping - the exact call-site ergonomics can vary by configuration, but the core idea is the same: construct the facet directly from the source entity, with the population logic already generated.

### Multiple facets from the same entity

```csharp
[Facet(typeof(User), exclude: [nameof(User.PasswordHash), nameof(User.CreatedAt)])]
public partial class UserSummaryDto;

[Facet(typeof(User), exclude: [nameof(User.PasswordHash)])]
public partial class UserDetailDto;

[Facet(typeof(User), include: [nameof(User.Id), nameof(User.Email)])]
public partial class UserContactDto;
```

This is Facet's core scenario - one domain entity, several different views needed for different contexts (a list summary, a detail page, a contact lookup), each generated from a single declarative line instead of three hand-maintained DTO classes plus three mapping profiles.

### Adding computed or custom properties alongside generated ones

```csharp
[Facet(typeof(User), exclude: [nameof(User.PasswordHash), nameof(User.FirstName), nameof(User.LastName)])]
public partial class UserDto
{
    public string FullName => $"{FirstName} {LastName}"; // if FirstName/LastName weren't excluded from source
}
```

Facet-generated classes are `partial`, which means you can extend them with additional hand-written members (computed properties, methods) alongside the generated ones - the same pattern that makes any source-generator-based partial class extensible.

## Core Workflow

- **Reach for `[Facet]` when the actual problem is "I need a focused view of this entity," not general type-to-type mapping.** This is a narrower, more specific tool than AutoMapper or Mapperly - using it outside that scenario is fighting the tool rather than benefiting from it.
- **Use `exclude` for "everything except a few sensitive or irrelevant fields," and `include` for "only these specific fields."** Choosing the right one keeps the declaration itself communicating intent clearly to the next reader.
- **Extend generated facets with `partial` for computed properties**, rather than generating the facet and then writing a separate wrapper or subclass to add derived data.

## Verifying Your Setup

1. **The generated DTO type actually appears** - confirm your IDE's "Go to Definition" on the facet class shows generated properties matching your domain model minus any excluded fields
2. **Mapping from the source entity works correctly** - confirm constructing a facet from a real entity instance populates every included property correctly
3. **Multiple facets from the same entity stay independently correct** - confirm each facet's field inclusion/exclusion matches its intended purpose, and that maintaining one doesn't accidentally affect another
4. **EF Core integration works, if used** - confirm Facet's EF Core `Include` handling (if you're using it for query projection) generates efficient, correct queries

## Best Practices

**Use Facet specifically for the "multiple views of one entity" pattern**, not as a general-purpose replacement for Mapperly or manual mapping across arbitrary type pairs. It's solving a narrower problem well, not trying to be everything.

**Name generated facets clearly by their purpose** (`UserSummaryDto`, `UserDetailDto`, `UserContactDto`), so the declarative attribute at the top of each file communicates intent immediately to anyone reading it.

**Extend facets with `partial` for computed properties rather than wrapping them.** This keeps the generated and hand-written parts of a DTO's definition in the same logical type, avoiding an extra layer of indirection.

**Go in aware this is a newer, less established tool than the rest of this comparison.** Its community and real-world adoption are still early-stage relative to AutoMapper, Mapster, or Mapperly - evaluate it as a deliberate bet on a specific, narrower capability, not as a like-for-like replacement for a general-purpose mapper.

**Keep sensitive fields (password hashes, internal-only data) excluded by default, and treat inclusion as the deliberate exception.** Given how directly Facet ties DTO shape to domain model structure, being explicit about what's excluded matters more here than with a hand-written DTO, where omission is naturally the default.

## Comparison with Mapperly

| | Facet | Mapperly |
| --- | --- | --- |
| What it generates | The DTO class itself, plus mapping code | Mapping code only - DTO must already exist |
| Scope | Narrower - focused views of domain entities | General-purpose type-to-type mapping |
| Mechanism | Compile-time source generator | Compile-time source generator |
| Maturity | Newer, smaller community | More established, growing fast |
| Best fit | "Multiple focused views of one entity" pattern | General mapping needs across arbitrary type pairs |

Both are source-generator-based and share the debuggability and compile-time-safety advantages that come with that architecture - the real difference is scope: Mapperly assumes your DTOs already exist, Facet assumes they don't need to be hand-written at all.

## Frequently Asked Questions

### What's the actual difference between Facet and a mapping library like Mapperly?

Mapperly generates the code that maps between two types you've already defined. Facet generates the destination type itself - the DTO class definition - alongside the mapping code, from a single declarative attribute on your domain model. Facet eliminates DTO boilerplate specifically; Mapperly eliminates mapping-logic boilerplate assuming the DTO already exists.

### Can I add custom properties to a Facet-generated class?

Yes - generated facet classes are `partial`, so you can add computed properties, methods, or other members in the same file (or a separate partial declaration) alongside the generated ones, the same extensibility pattern any source-generator-based partial class supports.

### Is Facet mature enough for production use?

It's newer and has a meaningfully smaller community and real-world adoption than AutoMapper, Mapster, or Mapperly. Evaluate it as a deliberate bet on its specific, narrower capability (DTO generation from domain models) rather than assuming equivalent ecosystem maturity to the more established general-purpose mappers in this comparison.

### When should I use include instead of exclude?

Use `include` when you want a genuinely minimal, specific subset of fields (like a contact-lookup DTO needing only ID and email) - it's clearer about intent than excluding a long list of everything else. Use `exclude` when the destination should mirror the source closely except for a small number of sensitive or irrelevant fields, which is usually the more common case for detail-view DTOs.

### Does Facet work well for generating multiple different views of the same entity?

Yes - this is Facet's core, best-fit scenario. Generating a summary DTO, a detail DTO, and a narrow contact DTO from the same domain entity, each via a single declarative attribute, is exactly the repetitive pattern Facet is designed to eliminate, compared to hand-maintaining three separate DTO classes and three separate mapping profiles.

### Should I replace my existing Mapperly or AutoMapper setup with Facet?

Not wholesale - Facet solves a narrower problem than general-purpose mapping. If your codebase's dominant pattern really is "multiple focused views of domain entities," it's worth evaluating for that specific use case. For general arbitrary type-to-type mapping needs, a general-purpose mapper like Mapperly remains the more appropriate tool, and the two can coexist for their respective strengths.

### What's the most common mistake when adopting Facet?

Trying to use it as a general-purpose mapping replacement for scenarios it wasn't designed for, rather than reserving it specifically for the "generate a focused view of a domain entity" pattern where it genuinely eliminates meaningful boilerplate. The second common mistake is not being deliberate about excluded fields, especially sensitive ones, given how directly the generated DTO's shape follows from the domain model's structure.

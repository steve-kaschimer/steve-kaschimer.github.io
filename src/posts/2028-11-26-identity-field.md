Identity Field stores a database identifier in an object so the persistence layer can maintain the connection between an in-memory entity and its database row. It sounds almost trivial because modern ORMs make it routine:
``` csharp
public sealed class Order
{
    public int Id { get; private set; }
}
```

But persistent identity is foundational to object-relational mapping.

## Object Identity vs. Database Identity

Two objects can contain identical data without representing the same business entity.
``` csharp
var first = new Customer("Ada", "ada@example.com");
var second = new Customer("Ada", "ada@example.com");
```

Are these two representations of one customer or two different customers? A persistent identifier answers that question across application processes and database transactions.
``` csharp
CustomerId(42)
```

means something very different from reference equality inside one .NET process.

## The Simplest Identity Field

A conventional EF Core entity might use:
``` csharp
public sealed class Customer
{
    public long Id { get; private set; }

    public string Name { get; private set; } = "";
}
```

EF Core recognizes `Id` by convention as the primary key. The object carries the same identity value used by its relational representation.

## Strongly Typed IDs

Primitive identifiers are convenient:
``` csharp
Task<Order?> GetAsync(long id);
```

but they make accidental mistakes easy:
``` csharp
await orders.GetAsync(customerId);
```

if both identifiers are `long`. Modern C# makes strongly typed identifiers inexpensive:
``` csharp
public readonly record struct OrderId(long Value);

public readonly record struct CustomerId(long Value);
```

Now an order can expose:
``` csharp
public sealed class Order
{
    public OrderId Id { get; private set; }
    public CustomerId CustomerId { get; private set; }
}
```

The compiler can help distinguish identities that happen to use the same storage type.

## Mapping a Strongly Typed ID

EF Core can convert the domain type to its database representation:
``` csharp
builder.Property(x => x.Id)
    .HasConversion(
        id => id.Value,
        value => new OrderId(value));
```

The database can still store a `bigint`, while the domain works with `OrderId`. This is a good example of Data Mapper allowing object and relational representations to differ.

## Generated Identity

Identifiers can be generated by the database:
``` sql
Id bigint generated by default as identity
```

or by the application:
``` csharp
public readonly record struct OrderId(Guid Value)
{
    public static OrderId New() => new(Guid.CreateVersion7());
}
```

Application-generated identifiers can be useful when an entity needs a stable identity before it is persisted. That can matter for:
-   domain events,
-   offline creation,
-   distributed workflows,
-   child entities that reference a new aggregate,
-   test fixtures.

The correct strategy depends on the system's requirements.

## Identity Should Usually Be Stable

Persistent identity should not normally change when business attributes change. A customer can change:
-   name,
-   email address,
-   billing address,
-   status.

The customer is still the same customer. That is why mutable business values often make poor primary identifiers.

## Natural vs. Surrogate Keys

A natural key comes from the business domain, such as a government-issued code or externally assigned number. A surrogate key exists primarily to identify the record:
``` csharp
OrderId(74219)
```

Natural keys can be useful when they are genuinely stable and unique. Surrogate keys often reduce coupling between business rules and persistence identity. An application can still enforce a natural value as an alternate key or unique constraint while using a surrogate primary key.

## Composite Identity

Some relational models identify rows with several columns. EF Core can map composite keys:
``` csharp
builder.HasKey(x => new
{
    x.OrderId,
    x.LineNumber
});
```

In the object model, you may choose to represent that identity explicitly:
``` csharp
public readonly record struct OrderLineId(
    OrderId OrderId,
    int LineNumber);
```

Whether that improves the domain depends on how frequently the composite identity is used outside persistence.

## Identity Field and Identity Map

Identity Field provides the persistent key. Identity Map uses that key to ensure the same database identity resolves to one in-memory object within a Unit of Work. Conceptually:
``` text
Identity Field: Customer.Id == 42

Identity Map:
42 -> Customer instance
```

The patterns solve different but complementary problems.

## Identity and Equality

Be careful not to confuse persistent identity with C# value equality. A record automatically provides value-oriented equality. That is excellent for value objects:
``` csharp
public readonly record struct Money(
    decimal Amount,
    string Currency);
```

Entities are different. Two entity instances with the same persistent ID may represent the same conceptual entity, but implementing equality solely around database IDs can create problems for transient entities that do not yet have assigned IDs. Choose entity equality semantics deliberately.

## DTOs and Public IDs

The database primary key does not necessarily need to be the identifier exposed outside the application. For example, an internal numeric key can coexist with a public identifier:
``` csharp
public sealed class Order
{
    internal long DatabaseId { get; private set; }

    public OrderId Id { get; private set; }
}
```

This can help separate storage concerns from public API contracts. Do not add multiple IDs automatically, though. Each identity scheme adds complexity.

## Testing

Strongly typed IDs can make tests clearer:
``` csharp
var orderId = new OrderId(42);
var customerId = new CustomerId(42);

Assert.NotEqual(
    orderId.ToString(),
    customerId.ToString());
```

Persistence tests should verify that generated and converted identifiers round-trip correctly through the actual database provider.

## When to Use It

If objects are persisted to a relational database, some form of persistent identity is almost unavoidable. The design choices are more interesting than the pattern's existence:
-   primitive or strongly typed,
-   database-generated or application-generated,
-   natural or surrogate,
-   single-column or composite,
-   internal or externally visible.

## Summary

Identity Field is simple but foundational. It creates the bridge between an object that exists temporarily in memory and an entity whose identity must survive processes, requests, and database transactions. Modern .NET makes strongly typed identities practical, while EF Core makes mapping them straightforward. The important part is choosing identity semantics intentionally rather than treating the primary key as an incidental database detail.

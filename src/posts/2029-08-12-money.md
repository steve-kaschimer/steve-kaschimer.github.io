Money represents a monetary amount together with its currency and
defines safe operations for arithmetic, comparison, rounding, and
allocation.

Using a bare `decimal` for money solves only part of the problem.

``` csharp
decimal total = 100m;
```

One hundred *what*?

USD? EUR? JPY?

Money makes the missing semantics explicit.

## A Basic Money Type

``` csharp
public readonly record struct Money(
    decimal Amount,
    Currency Currency);
```

with:

``` csharp
public readonly record struct Currency(string Code);
```

Now:

``` csharp
var price =
    new Money(
        19.99m,
        new Currency("USD"));
```

The amount and currency travel together.

## Why decimal?

For most business applications in .NET, `decimal` is the appropriate
primitive for base-10 monetary arithmetic:

``` csharp
0.1m + 0.2m
```

behaves as users expect for decimal quantities.

Binary floating-point types such as `double` are generally inappropriate
for ordinary financial amounts where exact decimal representation
matters.

But `decimal` alone does not solve:

-   currency compatibility,
-   rounding policy,
-   allocation,
-   minor-unit rules.

## Addition

You cannot safely add different currencies:

``` csharp
USD 10 + EUR 10
```

without an exchange-rate operation.

Enforce that rule:

``` csharp
public readonly record struct Money(
    decimal Amount,
    Currency Currency)
{
    public static Money operator +(
        Money left,
        Money right)
    {
        EnsureSameCurrency(left, right);

        return new Money(
            left.Amount + right.Amount,
            left.Currency);
    }

    private static void EnsureSameCurrency(
        Money left,
        Money right)
    {
        if (left.Currency != right.Currency)
        {
            throw new CurrencyMismatchException(
                left.Currency,
                right.Currency);
        }
    }
}
```

Now an invalid operation fails immediately.

## Multiplication

Multiplication by a scalar is meaningful:

``` csharp
public static Money operator *(
    Money money,
    decimal multiplier)
{
    return new Money(
        money.Amount * multiplier,
        money.Currency);
}
```

But multiplication often introduces fractions smaller than the
currency's minor unit.

That leads to rounding.

## Currency Metadata

A richer currency model can define minor units:

``` csharp
public sealed record Currency(
    string Code,
    int DecimalPlaces);
```

Examples:

``` text
USD -> 2
JPY -> 0
```

Do not assume every currency uses two decimal places.

## Rounding

Rounding policy is a business decision.

``` csharp
public Money Round(
    MidpointRounding mode =
        MidpointRounding.ToEven)
{
    return this with
    {
        Amount = decimal.Round(
            Amount,
            Currency.DecimalPlaces,
            mode)
    };
}
```

Some domains require a specific midpoint rule.

Others have regulatory or contractual rounding requirements.

Make the policy deliberate.

## When to Round

Suppose:

``` text
Unit price = 10.00
Tax rate  = 8.25%
Quantity  = 3
```

Possible policies include:

``` text
round tax per line
round tax per unit
round only invoice total
```

They can produce different results.

Money arithmetic must reflect the business rule, not merely the
available numeric API.

## Allocation

A classic Money problem is splitting an amount without losing pennies.

Suppose:

``` text
USD 10.00 / 3
```

You cannot return three equal two-decimal values whose sum is exactly
\$10.

A correct allocation might be:

``` text
3.34
3.33
3.33
```

The parts still sum to the original.

## Allocation Example

``` csharp
public IReadOnlyList<Money> Allocate(int parts)
{
    if (parts <= 0)
        throw new ArgumentOutOfRangeException(
            nameof(parts));

    var factor =
        Pow10(Currency.DecimalPlaces);

    var minorUnits =
        decimal.ToInt64(
            decimal.Round(
                Amount * factor,
                0,
                MidpointRounding.ToEven));

    var low = minorUnits / parts;
    var remainder = minorUnits % parts;

    var result = new Money[parts];

    for (var i = 0; i < parts; i++)
    {
        var units =
            low + (i < remainder ? 1 : 0);

        result[i] = new Money(
            units / factor,
            Currency);
    }

    return result;
}
```

Production implementations should carefully define behavior for negative
values and the domain's required rounding rules.

## Minor Units as Integers

Some systems store money as integer minor units:

``` text
$19.99 -> 1999 cents
```

This can simplify exact storage and interoperability with payment APIs.

But currencies with different minor-unit rules still require metadata.

Do not assume "cents" is universal.

## Exchange Rates

Currency conversion is not ordinary arithmetic.

Model it explicitly:

``` csharp
public readonly record struct ExchangeRate(
    Currency From,
    Currency To,
    decimal Rate);
```

Then:

``` csharp
public Money Convert(
    Money source,
    ExchangeRate rate)
{
    if (source.Currency != rate.From)
        throw new InvalidOperationException();

    return new Money(
        source.Amount * rate.Rate,
        rate.To);
}
```

A real system also needs:

-   rate source,
-   timestamp,
-   precision,
-   rounding policy.

## Equality

These are not equal:

``` text
USD 10
EUR 10
```

The currency is part of the value.

A record struct gives us natural value equality:

``` csharp
new Money(10m, Usd)
==
new Money(10m, Usd)
```

## Formatting

Formatting is presentation:

``` csharp
money.Amount.ToString(
    "C",
    cultureInfo);
```

Be careful not to infer the business currency solely from UI culture.

A user in Germany may still be viewing a USD account.

Currency and culture are related presentation concerns, not
interchangeable concepts.

## EF Core Complex Type Mapping

A Money value can be mapped as a complex type:

``` csharp
builder.ComplexProperty(
    x => x.Total,
    money =>
    {
        money.Property(x => x.Amount)
            .HasColumnName("TotalAmount")
            .HasPrecision(19, 4);

        money.Property(x => x.Currency)
            .HasColumnName("TotalCurrency");
    });
```

If `Currency` is itself a richer value object, configure its
representation appropriately.

## Database Precision

Never leave monetary precision accidental.

For SQL Server, explicitly choose a decimal precision and scale
appropriate to the domain:

``` csharp
.HasPrecision(19, 4);
```

The right scale is not always 2.

You may need more precision for:

-   intermediate calculations,
-   exchange rates,
-   unit prices,
-   financial instruments.

## Persistence vs. Display Precision

A system may store:

``` text
19.123456
```

while displaying:

``` text
19.12
```

Do not conflate database scale, calculation precision, and display
formatting.

Each serves a different purpose.

## JSON Contracts

A public API might represent money as:

``` json
{
  "amount": "19.99",
  "currency": "USD"
}
```

Using a JSON number is also possible, but external consumers and
languages may handle decimal precision differently.

For financial APIs, define the contract explicitly rather than relying
on serializer defaults.

## Never Use Money Without Currency at Boundaries

This is ambiguous:

``` json
{
  "total": 100
}
```

Prefer:

``` json
{
  "total": {
    "amount": 100,
    "currency": "USD"
  }
}
```

unless the API contract has an unambiguous currency defined elsewhere.

## Discounts

A discount percentage is not Money:

``` csharp
public readonly record struct Percentage(
    decimal Value);
```

Applying it produces Money:

``` csharp
var discount =
    subtotal * percentage.AsFraction();
```

Strong types help prevent mixing fundamentally different numeric
concepts.

## Tax

Tax calculations often expose why a Money type matters.

The domain needs explicit rules for:

-   taxable base,
-   rate precision,
-   rounding point,
-   jurisdiction,
-   inclusive vs. exclusive tax.

A Money object handles safe monetary arithmetic, but it does not replace
the domain's tax policy.

## Testing

Money deserves thorough tests.

Test:

-   same-currency addition,
-   currency mismatch,
-   multiplication,
-   positive and negative amounts,
-   zero,
-   rounding boundaries,
-   allocation remainders,
-   JPY-like zero-decimal currencies,
-   persistence precision,
-   serialization.

Property-based testing is especially useful for invariants such as:

``` text
sum(Allocate(n)) == original amount
```

## When to Use It

If the application performs meaningful monetary calculations, Money is
almost always preferable to passing bare decimals around.

## Summary

Money is a specialized Value Object that combines amount and currency
and defines the rules for safe monetary operations.

Modern C# records make the type concise, but the hard parts remain
domain decisions: currency compatibility, precision, rounding,
allocation, conversion, storage, and external representation.

Treating those decisions explicitly is what turns `decimal` into Money.

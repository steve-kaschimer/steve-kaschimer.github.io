Mapper moves data between two objects or subsystems that should remain
independent of each other.

The important phrase is **remain independent**.

Mapping is not merely copying properties. It is an architectural
boundary between models with different responsibilities.

## The Problem

Suppose an external billing provider returns:

``` csharp
public sealed record VendorInvoiceDto(
    string InvoiceId,
    long AmountDue,
    string CurrencyCode,
    string CustomerReference);
```

Your domain model should not have to understand `VendorInvoiceDto`.

Instead, a mapper translates:

``` csharp
public static Invoice ToDomain(
    VendorInvoiceDto source)
{
    return Invoice.Import(
        new InvoiceId(source.InvoiceId),
        Money.FromMinorUnits(
            source.AmountDue,
            source.CurrencyCode),
        new CustomerReference(
            source.CustomerReference));
}
```

The two models can evolve independently.

## Mapping Between Layers

Modern .NET applications commonly map between:

``` text
HTTP Request DTO
      |
Application Command
      |
Domain Model
      |
Persistence Model
      |
Database
```

and on reads:

``` text
Database
   |
Projection
   |
Response DTO
   |
JSON
```

Not every application needs every representation, but each mapping
boundary should have a reason.

## Explicit Mapping

For important mappings, plain C# is often excellent:

``` csharp
public static OrderResponse ToResponse(
    Order order)
{
    return new OrderResponse(
        Id: order.Id.Value,
        Number: order.Number.Value,
        Status: order.Status.ToString(),
        Total: new MoneyResponse(
            order.Total.Amount,
            order.Total.Currency));
}
```

Advantages include:

-   compile-time visibility,
-   easy debugging,
-   no hidden convention,
-   obvious contract decisions.

Modern C# makes this fairly concise.

## Extension Methods

Small mapping functions can read naturally as extension methods:

``` csharp
public static class OrderMappings
{
    public static OrderResponse ToResponse(
        this Order order)
        => new(
            order.Id.Value,
            order.Number.Value,
            order.Status.ToString(),
            order.Total.Amount);
}
```

Usage:

``` csharp
return Results.Ok(order.ToResponse());
```

Keep these methods near the boundary they serve rather than turning one
global mapping class into a dumping ground.

## Mapper Objects

When mapping requires dependencies, use an object:

``` csharp
public sealed class CustomerMapper(
    ICountryCodeResolver countries)
{
    public Customer ToDomain(
        ExternalCustomer source)
    {
        var country =
            countries.Resolve(source.CountryCode);

        return Customer.Import(
            source.Id,
            source.Name,
            country);
    }
}
```

The mapper remains responsible for translation rather than business
workflow.

## Mapping Libraries

Mapping libraries can remove repetitive code when two models have large
amounts of mechanical correspondence.

They are less attractive when mapping contains important semantic
decisions.

If this:

``` text
External Status = "A"
```

means:

``` text
Domain Status = AccountStatus.Active
```

the translation deserves to be visible and tested.

Do not hide meaningful domain interpretation behind convention merely to
reduce line count.

## Compile-Time Mapping

Source generators and compile-time mapping tools can provide a useful
middle ground:

-   less repetitive code,
-   compile-time feedback,
-   fewer reflection costs,
-   generated mapping visible to tooling.

The architectural question remains the same: should these two models be
coupled directly?

If not, a mapper boundary still has value regardless of how the mapping
code is generated.

## EF Core Projections

Sometimes the best mapper is the LINQ projection itself:

``` csharp
var orders = await db.Orders
    .Where(x => x.CustomerId == customerId)
    .Select(x => new OrderSummary(
        x.Id.Value,
        x.Number.Value,
        x.Status.ToString(),
        x.Total.Amount))
    .ToListAsync(cancellationToken);
```

This maps directly from persistence query to read model without
materializing full domain entities.

That can be both clearer and faster for read-only use cases.

## Mapper vs. Data Mapper

These names are easy to confuse.

**Mapper** is a broad base pattern for translating between independent
objects or subsystems.

**Data Mapper** specifically separates in-memory domain objects from
database persistence.

A Data Mapper is a specialized use of the more general mapping idea.

## Mapper vs. Gateway

Gateway isolates access to an external system.

Mapper translates between models.

They often work together:

``` text
Application
   |
Gateway
   |
Mapper
   |
Vendor SDK / API
```

The Gateway owns the interaction. The Mapper owns representation
translation.

## Mapper vs. DTO

A DTO is a data carrier.

A Mapper translates to or from it.

``` text
Domain Model
    |
  Mapper
    |
DTO
```

They solve complementary problems.

## Where Should Mapping Live?

Place mapping near the architectural boundary that owns the translation.

For example:

``` text
Infrastructure/
  Payments/
    VendorPaymentGateway.cs
    VendorPaymentMapper.cs
```

or:

``` text
Features/
  Orders/
    GetDetails/
      OrderDetailsResponse.cs
      OrderDetailsMapping.cs
```

Avoid a giant `Mappings` project containing unrelated translations with
no clear owner.

## Nullability

Mapping is a good place to resolve differences in null semantics.

An external API may return:

``` csharp
string? CountryCode
```

while your domain requires a country.

The mapper must decide whether to:

-   reject the input,
-   supply a default,
-   represent an unknown value,
-   return a failure.

That is a semantic decision, not merely property copying.

## Validation

Do not confuse mapping with validation.

A mapper can detect that a representation cannot be translated, but
domain invariants should still be protected by the domain.

For example:

``` csharp
Customer.Create(name, email)
```

should remain valid regardless of whether input originated from HTTP, a
queue, or an import.

## Testing

Mapping tests are especially valuable at boundaries.

Test:

-   enum translations,
-   units and currencies,
-   null semantics,
-   date/time conversions,
-   identifiers,
-   renamed fields,
-   unsupported external values.

Simple one-to-one property copying rarely needs exhaustive tests.

## When to Use It

Mapper is useful whenever two models should vary independently.

Typical examples include:

-   domain ↔ API DTO,
-   external API ↔ application model,
-   persistence representation ↔ domain model,
-   legacy model ↔ modern model.

## When to Avoid Extra Mapping

If two types exist only because an architecture diagram says every layer
must have its own model, the mapping may be ceremony.

Independence has a cost.

Create separate models when their responsibilities, lifecycles, or
change pressures are genuinely different.

## Related Patterns

-   Data Mapper
-   Gateway

## Summary

Mapper protects independence between models by making translation
explicit.

Modern C# makes manual mapping concise, while projection and
source-generation tools can reduce mechanical work.

The goal is not to eliminate mapping code. It is to spend mapping code
where it buys architectural independence.

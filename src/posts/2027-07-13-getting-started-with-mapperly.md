Mapperly asks you to declare a partial method with the shape you want - source type in, destination type out - and then writes the actual mapping body for you at compile time. There's no runtime configuration to register, no reflection happening anywhere; the method you call in production is real, generated C# code sitting right next to your own, which you can open and read like any other file in your project.

This guide covers installing Mapperly, bootstrapping mapper classes and understanding the partial-method pattern that drives everything, the core configuration attributes for property renaming and custom logic, and the best practices for getting Mapperly's full performance and safety benefit without fighting its compile-time nature. By the end you'll have fast, debuggable, compile-time-checked mapping code - and a clear sense of why this is the recommended starting point for a new project in 2026.

If you're deciding between mapping approaches first, [a comparison of the top .NET mapping libraries](/posts/2027-06-22-top-5-dotnet-mapping-libraries-compared/) covers where Mapperly fits relative to AutoMapper, Mapster, manual mapping, and Facet.

## What You'll Need

- .NET 8 SDK or later
- A recent C# language version, since Mapperly relies on source generators and partial method bodies

## Installing Mapperly

```bash
dotnet add package Riok.Mapperly
```

That's the entire installation - no separate tool, no runtime package. Mapperly operates purely through source generation triggered by the compiler.

## Bootstrapping the Ideal Environment

### A basic mapper

```csharp
using Riok.Mapperly.Abstractions;

[Mapper]
public partial class OrderMapper
{
    public partial OrderDto ToDto(Order order);
}
```

That's a complete, working mapper. The `[Mapper]` attribute tells Mapperly's source generator to look at this class; the `partial` method declaration with no body is what it fills in, generating real, readable C# that maps matching property names automatically - similar convention-based behavior to AutoMapper and Mapster, but resolved entirely at compile time.

### Viewing the generated code

You can inspect exactly what Mapperly produces via your IDE's "Go to Definition" on the generated partial, or by checking your build's generated files output. It looks like straightforward, hand-written C# - explicit property assignments, null checks, nothing opaque:

```csharp
// Generated by Mapperly (illustrative)
public partial OrderDto ToDto(Order order)
{
    if (order == null) return default;
    var target = new OrderDto();
    target.Id = order.Id;
    target.Status = order.Status;
    return target;
}
```

This is the concrete payoff of Mapperly's architecture - you can set a breakpoint inside this generated method and step through it exactly like you would your own code, something not meaningfully possible with AutoMapper's reflection/expression-tree internals.

### Handling renamed and nested properties

```csharp
[Mapper]
public partial class OrderMapper
{
    [MapProperty(nameof(Order.Customer) + "." + nameof(Customer.Name), nameof(OrderDto.CustomerName))]
    public partial OrderDto ToDto(Order order);
}
```

`[MapProperty]` handles both renaming and flattening nested properties - Mapperly also infers straightforward flattening automatically in many common cases without needing the attribute explicitly, but being explicit is worth it wherever the mapping isn't immediately obvious to a future reader.

### Custom mapping logic for a specific property

```csharp
[Mapper]
public partial class OrderMapper
{
    [MapProperty(nameof(Order.Price), nameof(OrderDto.FormattedPrice), Use = nameof(FormatPrice))]
    public partial OrderDto ToDto(Order order);

    private static string FormatPrice(decimal price) => price.ToString("C");
}
```

The `Use` parameter points Mapperly at a method you've written for that specific property's conversion logic - the generated code calls your method directly, keeping custom logic explicit and debuggable rather than hidden behind a runtime callback registration.

### Ignoring properties and enum mapping strategy

```csharp
[Mapper(EnumMappingStrategy = EnumMappingStrategy.ByName)]
public partial class OrderMapper
{
    [MapperIgnoreSource(nameof(Order.InternalNotes))]
    public partial OrderDto ToDto(Order order);
}
```

`EnumMappingStrategy.ByName` is worth setting explicitly whenever source and destination enums might have different underlying numeric values - without it, Mapperly maps by numeric value by default, which silently produces wrong results if the two enums aren't numbered identically.

## Core Workflow

- **Declare a partial method per mapping direction you need, and let Mapperly fill in the body.** This is the entire core pattern - resist looking for a separate configuration file or fluent setup API, since the method signature itself is the configuration surface.
- **Use `[MapProperty]` for anything that doesn't match by convention**, the same principle every mapper in this comparison shares - configure exceptions, not the whole mapping.
- **Check the generated code when something doesn't behave as expected.** Because it's real, inspectable C#, debugging a Mapperly mapping issue means reading actual generated logic, not reasoning about a runtime library's internal reflection behavior.

## Verifying Your Setup

1. **The mapper compiles and generates code** - confirm your partial method actually gets a generated implementation (visible via "Go to Definition")
2. **Renamed and nested properties map correctly** - confirm `[MapProperty]` configurations produce the expected result
3. **Enum mapping strategy matches your intent** - if source and destination enums have different numeric values, confirm `EnumMappingStrategy.ByName` is set and enums map by name, not by (potentially mismatched) number
4. **Compile-time errors catch real mistakes** - deliberately introduce a typo in a `[MapProperty]` reference and confirm it's a build error, not a silent runtime issue

## Best Practices

**Trust the partial-method pattern rather than looking for AutoMapper-style runtime configuration.** The method signature and its attributes are the entire configuration surface - there's no separate profile or startup registration step to find.

**Set `EnumMappingStrategy.ByName` explicitly whenever enum numeric values might not align between source and destination.** This is one of the more common silent-bug risks in enum mapping across every library in this comparison, and Mapperly makes it a deliberate, explicit choice rather than an assumption.

**Read the generated code when debugging, not just the attributes.** Mapperly's debuggability is a real, concrete advantage - use it directly rather than treating the generated output as a black box the way you might with a reflection-based mapper.

**Adopt Mapperly for new projects and genuine rewrites, not as a profile-by-profile migration from an existing AutoMapper codebase.** The configuration models are different enough that piecemeal migration tends to be slower and more error-prone than a clean-slate approach.

**Use `[MapperIgnoreSource]`/`[MapperIgnoreTarget]` deliberately for properties that shouldn't be mapped**, rather than letting Mapperly's convention silently map something you didn't intend to expose.

## Comparison with AutoMapper

| | Mapperly | AutoMapper |
| --- | --- | --- |
| Mechanism | Compile-time source generator | Runtime reflection/expression trees |
| Configuration | Partial method + attributes | `Profile` classes registered at startup |
| Performance | Fastest, on par with manual mapping | Slowest of the dedicated mappers |
| Debuggability | Excellent - step into generated code | Harder - reflection/expression internals |
| License | Free, MIT | Commercial (2025+), free community tier |
| EF Core ProjectTo equivalent | Available, less battle-tested | Mature, widely used |

Mapperly is the clear "starting fresh today" choice on technical merits and licensing - AutoMapper's remaining edge is specifically around `ProjectTo`'s maturity for EF Core-heavy projection scenarios.

## Frequently Asked Questions

### Why does my Mapperly method need to be partial with no body?

That's the mechanism the source generator hooks into - you declare the method signature (what types are involved), and Mapperly's generator provides the implementation at compile time. This is fundamentally different from AutoMapper's runtime `Map<T>()` call, which resolves mapping logic dynamically rather than generating a real method body ahead of time.

### Can I see the actual code Mapperly generates?

Yes - via your IDE's "Go to Definition" on the partial method, or by inspecting your build's generated files output directly. This is one of Mapperly's most concrete advantages: the mapping logic is real, readable, steppable C#, not a black-box runtime mechanism.

### How do I map properties with different names between source and destination?

Use `[MapProperty(nameof(Source.Property), nameof(Destination.Property))]` on the partial method. Mapperly also infers some flattening patterns automatically, but being explicit is worth it for anything that isn't immediately obvious to someone reading the mapper later.

### Why did my enum mapping produce wrong values?

Most likely because source and destination enums have different underlying numeric values, and Mapperly's default enum mapping strategy maps by numeric value rather than by name. Set `[Mapper(EnumMappingStrategy = EnumMappingStrategy.ByName)]` explicitly whenever this is a possibility - it's a common, easy-to-miss source of silent bugs.

### Should I migrate my existing AutoMapper profiles to Mapperly one at a time?

Generally not recommended - the configuration models are different enough (partial methods and attributes vs. `Profile` classes and fluent configuration) that a piecemeal, profile-by-profile migration tends to be slower and more error-prone than a clean rewrite. Mapperly fits best for new projects or services already being substantially rewritten.

### Does Mapperly support mapping collections and nested objects automatically?

Yes - Mapperly handles collection mapping (lists, arrays, and other common collection types) and nested object graphs as part of its core convention-based behavior, generating the appropriate iteration and recursive mapping code automatically for matching structures.

### What's the most common mistake in a first Mapperly setup?

Not setting `EnumMappingStrategy.ByName` when source and destination enums have different numeric values, leading to silently wrong mapped results. The second common mistake is attempting a large, incremental migration from an existing AutoMapper codebase rather than reserving Mapperly for new or substantially rewritten code where its different configuration model fits more naturally.
